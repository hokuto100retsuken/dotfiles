現在のブランチからPRを作成する。

## 手順

### 1. 機械チェック（先に通す）

`bash ~/src/github.com/hokuto100retsuken/dotfiles/claude/scripts/pre-pr-check.sh` を実行する。
指摘が出たら、PR本文を書き始める前に対応する（BLOCK は必須修正、WARN は意図的かどうかユーザーに確認）。

> `gh pr create` 時に hook で同じチェックが走るため、ここを飛ばしても最終的に止まる。

### 2. 差分の把握

- base ブランチを特定（`git symbolic-ref refs/remotes/origin/HEAD` → 無ければ master / main）
- base が master/main 以外なら**依存元PRがある**。そのPR番号とマージ順を控える
- `git diff <base>...HEAD` と `git log <base>..HEAD` で変更内容を把握

### 3. 仕様ソースの収集（レビュー指摘の最頻帯）

差分だけ見て本文を書かない。以下を集めてから書く。

- **issue**: ブランチ名 / コミットメッセージ / 既存PR本文から issue 番号（`#NNNN`・`colorme/xxx#NNNN`）を抽出し、
  `GH_HOST=git.pepabo.com gh issue view <番号> -R colorme/<repo>` で要件を取得
- **仕様書**: `~/src/git.pepabo.com/colorme/trunk` を差分のキーワードで grep し、該当ドキュメントを読む
- **Notion / Slack**: issue 本文・コメント中の Notion / Slack URL を抽出し、
  `notion-fetch` / `slack_read_thread` で内容を取得（どちらも許可済み）

集めたら差分と1対1で突き合わせ、**次の点に齟齬や未確認がないか**検査する：

- 判定条件・状態のマッピングが仕様と一致しているか。全パターンを列挙して、どこにも入らない／どちらにも入りうる状態がないか
- 判定の粒度（ショップ単位 vs 種別単位、アカウント単位 vs 注文単位）
- 「この場合は対象外」と決まった例外が抜けていないか
- 画面文言・メール文面が確定版と一字一句一致しているか。用語が既存の呼称と揃っているか

**齟齬や確信の持てない点があれば、PRを作らずユーザーに選択肢付きで確認する。**

### 4. push

ブランチが未 push なら `git push -u origin <branch>`。

### 5. PR本文の構築

`.github/PULL_REQUEST_TEMPLATE.md` があれば**その `##` 見出しとチェックリストは動かさない**。
colorme-admin / colorme-api のテンプレートは `## 何を解決するのか` / `## レビューポイント` /
`## リリース時期` の3つで、**足す内容はその配下に `###` で入れ子にする**。
見本もそうしている（`### 動作確認方法` と `### 本PRで対応していないこと` は
`## レビューポイント` の配下）。テンプレートが無いリポジトリでは `##` で並べてよい。

見本: [colorme-admin#21214](https://git.pepabo.com/colorme/colorme-admin/pull/21214) /
[#21206](https://git.pepabo.com/colorme/colorme-admin/pull/21206) /
[colorme-api#10337](https://git.pepabo.com/colorme/colorme-api/pull/10337)（いずれも suda-k）

| 見出し | 位置 | 中身 |
|---|---|---|
| `## 何を解決するのか` | テンプレ | **この PR で何をするのかを1文で言い切る**（「完了判定を fincode 用の条件に差し替えます」「残り日数の不具合を修正する」）。次に、そうする必要がある理由を具体的なシンボルで示す（`f_ChkNyukinSimeDate()` が残契約日数を返していた 等）。`Closes <フルURL>` を置く |
| `### 本番の影響件数` | 上の配下・該当時 | 実データの件数表。状態ごとに件数と表示を並べる。**数を出せる場面で出さないと「たぶん影響ない」で通してしまう** |
| `### 変更点` | 上の配下・必須 | Before / After 表、または箇条書き。判定条件を変えたなら旧条件と新条件を並記する |
| `## レビューポイント` | テンプレ | **判断ごとに1項目**で「なぜそうしたか」。行に紐づくものは手順7のインラインに置き、本文には**件数で誘導する**（「インラインコメント（7件）に書いています」）。テストは スイート名 + examples 数 |
| `### セルフレビューで洗い出したエッジケース` | 上の配下・該当時 | ケース / 件数 / 挙動 の表。nil・0件・異常値をどう倒したか |
| `### 動作確認方法` | 上の配下・必須 | 前提条件（定数やフラグの一時変更が要るならその手順）＋番号付き手順。**やっていないことは「未実施」と書く** |
| `### ご相談: <論点>` | 上の配下・該当時 | 判断を仰ぐ論点。**事実（帰結）を先に書き、決めることを1つに絞る**（`no-meta-commentary.md` の例外） |
| `### 本PRで対応していないこと` | 上の配下・必須 | スコープ外＋理由＋委ねる先。「別issueに委ねる」なら**なぜそちらでやる方が良いか**まで書く |
| `## リリース時期` | テンプレ | フラグで隠れているか、いつ出すか、依存PRとのマージ順 |

base が master/main 以外なら、依存PR番号とマージ順を `## リリース時期` に必ず書く。

冒頭を太字にする必要はない。**強調は譲れない制約に使う**
（「フラグ無効時の挙動は現行のまま維持します」「B は別issueへ委ねるため close しない」）。
全部太字にすると効かなくなる。

生成バッジ（Generated with Claude Code 等）は入れない。

#### チェックリストは自分の分だけ埋める

- **`（※レビュー依頼者はチェックしないでください）` の節は触らない。**
  `## セキュリティレビュー（Reviewer用）` `## その他のレビュー（Reviewer用）` と、
  `### デザイナーは…` の **レビュアー**側。`<!-- ai-review:reviewer-checkbox ... -->` の
  マーカーも消さない
- 埋めるのは `## レビューを依頼する前に` と `### デザイナーは…` の **作業者**側、
  `### HTMLやPHPを変更した際は…`、`## マージの前に`
- **該当しない項目も「該当しないことを確認して」チェックする**のがテンプレートの指示。
  ただしブラウザ確認のように**実際にやっていない項目は埋めない**。
  未実施のままレビューに出してよいかはユーザーに聞く

#### 書けない欄はユーザーに聞く（勝手に埋めない）

骨格の欄が埋まらないのは、たいてい**まだ決まっていない**ため。推測で埋めず、本文を作る前に聞く。
選択肢を付けて聞き、答えをそのまま本文に落とす。

| 聞くこと | 聞き方の例 |
|---|---|
| 影響件数を出すか | 「本番データで件数を出しますか（クエリを書きます）。それとも影響範囲の説明だけにしますか」 |
| 挙動変更を許容するか | 「この変更で〜ができなくなります。許容してよいですか / ガードを足しますか」 |
| スコープ外の扱い | 「〜は今回やらない想定です。別issueを立てますか / この PR に含めますか」 |
| 動作確認の範囲 | 「テストは通っています。ブラウザ確認も必要ですか」 |
| リリースの前提 | 「フラグ無効なので本番表示は変わりません。この理解で合っていますか」 |
| 用語・文言 | 「画面文言は〜にしています。確定版と一致していますか」 |

**確信の持てない点を PR に書かずに済ませない。** 決まっていないなら聞く、聞けないなら
`### ご相談` としてレビュアーに残す。黙って一方に倒すのが一番まずい。

### 6. 作成

`gh pr create --draft` で作成する（必ず `--draft`。Ready化はユーザー判断なので `gh pr ready` はしない）。

- タイトル: 変更内容を簡潔に（70文字以内）
- 本文: 日本語 Markdown

### 7. 自己注記（レビュー依頼前に差分へ根拠を貼る）

指摘の最多カテゴリは実装ミスではなく**「判断の根拠が差分から読めないので聞かれる」**質問。
持っている情報を、聞かれる前に該当行のインラインコメントとして置く。PR本文ではなく**行に貼る**
（レビュアーは差分を読むため）。

#### ラベルを付けて種類を分ける

先頭に太字のラベル＋一行サマリを置く。レビュアーが「読むだけでよい」注記と
「返事が必要」な注記を判別できるようにする。

| ラベル | 使う場面 |
|---|---|
| `**要確認（挙動変更）: <一行>**` | 既存の挙動が変わる。**誰が何をできなくなるか**を書き、許容可否を仰ぐ |
| `**確認したいこと: <一行>**` | 仕様に明記がなく、こちらで決めた。判断を仰ぐ |
| `**レビューポイント: <一行>**` | 非自明な実装判断の理由。返事は不要 |
| `**スコープ外だが含めた変更: <一行>**` | この PR の範囲外だが入れた。入れないと何が壊れるかを書く |
| `**<何>した理由（セルフレビューで発覚）**` | 自分で見つけた問題への対応 |

#### 各注記の中身は同じ順で書く

1. **変更前はどうだったか** — 移設元・旧条件を具体的なシンボルで（`Product::ofAccount()->Enabled()` は `del_flg=0` のみ）
2. **変更後の具体的な帰結** — 「〜のショップは利用申請に進めなくなります」。抽象語で濁さない
3. **その選択の理由** — 仕様・審査要件・既存実装のどれに基づくか
4. **判断を仰ぐならここで1つだけ** — 「運用上許容できるかご判断ください」
5. **テストで担保しているなら test 名** — `ColormePaymentPrerequisitesTest::isShopOpen_開店中ならtrueを返す`

#### 貼る行（過去に実際に聞かれた箇所）

| # | 対象の行 | 貼る内容 |
|---|---|---|
| 1 | 外部API のパラメータ・挙動に依存する行 | fincode 等の公式ドキュメント URL |
| 2 | 仕様書 / issue / Notion の合意で決まった判定条件 | ref URL（セクションのアンカーまで） |
| 3 | 口頭・Slack で決まったこと | 「口頭で〜と決まった」と明記（Slack なら permalink） |
| 4 | nil・あり得ないケースを通した / 通さなかった行 | 許容した理由、または例外にした理由 |
| 5 | 既存実装を踏襲した行 | 参考にした既存コードの permalink |
| 6 | 意図的に今回やらなかったこと | 後続 issue 番号 |
| 7 | 新しい用語・クラス名を導入した行 | その語の由来（既存コードの多数派でないなら特に必須） |
| 8 | 通常と違うテスト手法を選んだ行 | WebMock / VCR のどちらを選んだ理由 |
| 9 | 既存の挙動を変えた行 | 変更前の条件と、変わることで生まれる新しい失敗モード |

とくに 2（仕様の出どころ）と 4（nil 方針）が指摘の最頻帯。この2つは必ず走査する。

#### 書き方

- 「〜だと思います」ではなく「〜のためこうしている」と確定形で書く
- **判断を仰ぐのは書いてよい**（`no-meta-commentary.md` の例外）。ただし事実と帰結を先に書き、
  決めることを1つに絞る。「どうしましょう」「案A/B/C」は書かない
- 参照は `ref: <URL>`
- **差分が変わって注記が outdated になったら貼り直す。** 古い注記が残ると読み手が混乱する

#### 本文との分担

本文の `## レビューポイント` には**行に紐づかない判断**だけを書き、行に紐づくものは注記に置いて
本文から件数で誘導する。両方に同じ内容を書かない。

#### 投稿

差分を読んで下書きを作り、**ユーザーに確認してから投稿する**（勝手に投げない）。

```bash
# comments.json: {"event":"COMMENT","comments":[{"path":"...","line":42,"side":"RIGHT","body":"ref: ..."}]}
GH_HOST=git.pepabo.com gh api -X POST \
  /repos/colorme/<repo>/pulls/<番号>/reviews --input comments.json
```

`line` は差分の**変更後**の行番号。削除行に貼るなら `side=LEFT` と変更前の行番号を使う。

**投稿後に反映件数を検算する。** GHE は複数インラインの一部を黙って落とすことがある
（memory `reference_ghe_review_inline_comment_dropped.md`）。
