コードレビューを実行する。引数あり（URL / PR番号）ならそのPRを、なければ現在のブランチ差分をレビューする。

## 引数

- `$ARGUMENTS` が空 → 現在ブランチの差分レビュー
- `$ARGUMENTS` に URL または PR番号が含まれる → 指定PR のレビュー

## 手順（引数なし: ブランチ差分レビュー）

1. base ブランチを特定（`git symbolic-ref refs/remotes/origin/HEAD` → 無ければ master / main）
2. `git diff <base>...HEAD` と `git status` で差分を取得
3. 以下の観点でレビュー：
   - バグやロジックの誤り
   - セキュリティ上の問題
   - パフォーマンスの懸念
   - テストの網羅性
   - 命名やコードの読みやすさ
4. 問題があれば具体的な修正案を提示、なければ「LGTM」と伝える

## 手順（引数あり: 他人の PR をレビューする）

### 1. PR と既存レビューの状況を取得

```bash
GH_HOST=git.pepabo.com gh pr view <PR> -R colorme/<repo> --json title,body,author,baseRefName,files,url
GH_HOST=git.pepabo.com gh pr diff <PR> -R colorme/<repo>
```

**既存の指摘を必ず先に読む。**同じことを二度言わない、解決済みを蒸し返さないため。

```bash
GH_HOST=git.pepabo.com gh api graphql -f query='
query($o:String!,$r:String!,$n:Int!){ repository(owner:$o,name:$r){ pullRequest(number:$n){
  reviewThreads(first:100){ nodes{ isResolved path line
    comments(first:10){ nodes{ author{login} bodyText } } } }
  reviews(first:50){ nodes{ author{login} state } } } } }' \
  -F o=colorme -F r=<repo> -F n=<PR>
```

- 既出の指摘は出さない。既出に**追加の根拠**を出せるならスレッドへの返信にする
- `isResolved: true` は蒸し返さない
- PR 作者自身の注記（`ref:` / `📝`）は既に確認済みの事項。そこを質問し直さない

### 2. 仕様ソースを集める（差分だけ見てレビューしない）

このチームで最も多い指摘は「仕様・合意との齟齬」。差分から仕様は分からないので先に集める。

- **issue**: PR本文・ブランチ名から番号を抽出し `gh issue view <番号> -R colorme/<repo>`
- **仕様書**: `~/src/git.pepabo.com/colorme/trunk` を差分のキーワードで grep
- **Notion / Slack**: issue・PR本文中の URL を `notion-fetch` / `slack_read_thread` で取得
- **外部APIの公式ドキュメント**: 決済プロバイダのパラメータを触っている差分では必ず当たる
  （実績: #9506「konbini_code がドキュメントに見つからない」#9666「amount は string で送られてくる」）
  fincode は SPA で WebFetch 不可。`fincode-sdk-node` と `mcp__fincode__*` を一次情報源にする

### 3. 観点リストを1項目ずつ当てる

下の「過去に指摘された観点」を開き、順に当てる。思いつきでレビューしない。

### 4. 指摘を下書きしてユーザーに確認

投稿前に必ず全文をユーザーに見せる。**勝手に投稿しない。** approve / request changes の判断はユーザーが行う。

### 5. 投稿

```bash
# review.json: {"event":"COMMENT","body":"全体コメント（任意）","comments":[
#   {"path":"app/models/foo.rb","line":42,"side":"RIGHT","body":"..."}]}
GH_HOST=git.pepabo.com gh api -X POST /repos/colorme/<repo>/pulls/<PR>/reviews --input review.json
```

`event` は `COMMENT` / `APPROVE` / `REQUEST_CHANGES`。既存スレッドへの返信は
`POST /repos/.../pulls/<PR>/comments` に `in_reply_to` を付ける。

## 観点リスト（必ず通す）

一般的な観点より、このチームで実際に指摘されているのは以下。過去のレビューコメントから作成した。
差分を見る前に必ずこのリストを開き、1項目ずつ当てる。自分がレビューする側でも同じリストを使う。
`実績:` は実際にその指摘が出た PR 番号。

### 仕様との突き合わせ（最頻）
- 判定条件・状態のマッピングが、issue / 仕様書 / Notion / Slack の合意と一致しているか
- 状態やステータスの分類は全パターンを列挙し、どこにも入らない／どちらにも入りうる状態がないか
- 判定の粒度は正しいか（ショップ単位 vs 種別単位、アカウント単位 vs 注文単位）
- 過去に「この場合は対象外」と決まった例外が抜けていないか
- 画面文言・メール文面が確定版と一致しているか。用語が既存の呼称と揃っているか

### 既存機能への副作用
- この変更で消える／上書きされるデータはないか
- 継続するはずの機能（計測タグ、設定値など）を巻き添えで消していないか

### nil / 件数の前提
- null を許容する必要が本当にあるか。null 時のフォールバックが表示を壊さないか
- `where` で複数件取る前提が実態と合っているか
- 「あり得ない」ケースを黙って握りつぶしていないか（例外を投げるべきでは）

### 対称性
- 同型の処理が複数ある場合、実装もテストも全部に反映されているか。片方だけになっていないか

### 残骸・後始末
- TODO コメント、デバッグコード、文字化けコメント、使わない定数／カラムが残っていないか
- 依存元PRの最新差分を取り込んでいるか。マージ順の前提がPR本文に書かれているか
- 「なぜこの対応が必要か」「どの入口からのフローか」がコードコメントとPR本文にあるか

### スキーマ変更
- 追加したカラムを実際に使う画面／処理があるか
- NULL 許容とデフォルト値が要件と合っているか
- 既存データの移行コスト・リリース後の対応負荷を考慮しているか

### データ更新SQL
- トランザクションで囲んでいるか。想定行数の検証があるか

### トランザクション境界・競合
- 判定に使う値の読み取りがトランザクションの外に出ていないか（読んだ後に別プロセスが変えうる）
- 一連の状態更新が同一トランザクションに入っているか。片方だけコミットされる窓がないか
- 1トランザクション内で外部API を複数回呼んでいないか（ロールバックしても外部の状態は戻らない）
- 実績: #9666「amount_mismatch チェックがトランザクション外」#9512「ここトランザクションで囲わなくて大丈夫ですか」#9575「status 更新もトランザクションに含めた方が良さそう」

### クエリ数・バッチ件数
- 同じ目的で複数回クエリを投げていないか。1本にまとめられないか（preload 分も数える）
- バッチで全件ロードしていないか。`find_each` / `in_batches` を使うべきでないか
- 先に絞り込めば減る無駄なクエリがないか
- 実績: #9670「preload も含めると4クエリ」「in_batches か find_each の利用を検討」#9488「配送済みも絞り込むと無駄なクエリが減る」#9628「個別に post すると実行時間がかかる」

### 例外の扱い
- 例外を握りつぶして元の情報を失っていないか（rescue の中で別の例外が出ると原因が消える）
- 失敗しても誰にも知らされないパスがないか
- 到達しないはずのコードを防御的に残していないか。あり得ないなら例外を投げるべきでは
- 実績: #9769「deliver_later が失敗すると元の PaymentError が失われる」#9438「Sekrets が読み込まれなくても何も知らせず起動する」#9647「実運用では到達しないデッドコードに見える」

### 責務の置き場所・命名空間
- 特定の関心事のコードがコントローラや巨大モデルに散らばっていないか。専用クラスに寄せられないか
- 前提が変わって意味を失った名前空間・クラス名のままになっていないか
- 実績: #10215「エラーに関するコードがコントローラーの中に散乱している」#9667「再決済関係なくなったのに Repayment の namespace」#9394「lib/fincode/ 以下に置いてファイル名を分けた方がよいかも」

### 追加したのに使われていないもの
- 新規の引数・設定値・クラス・カラム・`dry_run` 等のフラグに、実際の利用箇所があるか
- 一箇所でしか使わないラッパーメソッドを増やしていないか
- 実績: #9394「この引数使われているようにみえないんですが」「この追加は不要そう」#9627「このクラスって使われてますかね」#9488「dry_run は不要かな」#9446「このラッパーメソッド一箇所でしか使われてない」

### テストは足すより削る
- 「このテストが落ちるとき、どの実装バグを捕まえているか」を1行で言えるか。言えないなら消す
- 下位クラスでテスト済みの振る舞いを上位でも再テストしていないか
- 境界値でない値を複数パターン並べていないか
- 使わなくなった機能のテストが残っていないか
- 実績: #9512「lib クラスでやってるテストケースなのにわざわざここでも必要か」#9446「境界値でもないですし100と10、どちらかだけでいいのでは」#9667「そもそもテストコード自体が不要」

### モックの選択（決済など外部API）
- クリティカルな決済系で WebMock 手書きスタブになっていないか。VCR で実レスポンスを使うべきでは
- 逆に、テナント管理など重要度の低いAPI操作で VCR を強制していないか
- 実績: #9479「決済系の操作ですが WebMock ではなく VCR にしなくて大丈夫ですか」#9394「決済系はクリティカルなので VCR での再現でよさそう」

### 冪等性・再送
- Webhook / 通知の受信が再送で二重処理にならないか
- 署名検証の失敗時に、再送を招くレスポンスを返していないか
- 実績: #9450「署名検証に失敗した場合に再送されても困るため正常処理と同じレスポンスを返す」#9448 冪等キーに UUID v4

## 出力形式

- 観点ごとに見出しを立てて箇条書き
- 各指摘に対象ファイル / 行番号を添える
- 重要度（blocker / nit）を明示
- 些細なスタイルの指摘（nit）は基本的に省略、重要な問題（blocker）だけ指摘する
- ただし**仕様との齟齬が疑われる点は、確信が持てなくても「確認」として必ず出す**（黙って正しいと判断しない）

## 他人の PR に書くときの書き方

このチームの既存のレビューに合わせる。断定して直させる形にしない。

- **疑問形で書く**: 「〜で大丈夫ですかね？」「〜と思ったのですがどうでしょうか？」。
  実装者の方が文脈を持っている前提で聞く
- **根拠を添える**: 公式ドキュメントの URL、既存実装の permalink、仕様書の該当箇所。
  根拠なしの好みは出さない
- **スコープを明示する**: 今のPRで直してほしいのか、別PRでよいのかを書く。
  例「このPRで対応しなくてもよいのですが」「対応自体は別PRで良いと思いました」
- **重要度を接頭辞で示す**: 軽いものは `[nits]` を付ける
- **修正案は suggestion ブロックで出す**: そのまま適用できる形にする

  ~~~
  ```suggestion
  修正後のコード
  ```
  ~~~

- **確認して問題なかったことも記録する**: 仕様や外部ドキュメントに当たって正しいと確認できた箇所は、
  `ref: <URL>` や末尾 `📝` で根拠を残す。後から読む人と実装者の両方に効く。
  問題がないなら `👍` / `👌` で確認済みを示す
- 事実と質問だけ書く。呼びかけ・相談文・推奨アクションの押し付けは入れない
