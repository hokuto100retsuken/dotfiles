コードレビューを実行する。引数あり（URL / PR番号）ならそのPRを、なければ現在のブランチ差分をレビューする。

## 引数

- `$ARGUMENTS` が空 → 現在ブランチの差分レビュー
- `$ARGUMENTS` に URL または PR番号が含まれる → 指定PR のレビュー

## 手順（引数なし: ブランチ差分レビュー）

1. base ブランチを特定（`git symbolic-ref refs/remotes/origin/HEAD` → 無ければ master / main）
2. `git diff <base>...HEAD` と `git status` で差分を取得
3. 以下の観点でレビュー：
   - バグやロジックの誤り
   - セキュリティ上の問題
   - パフォーマンスの懸念
   - テストの網羅性
   - 命名やコードの読みやすさ
4. 問題があれば具体的な修正案を提示、なければ「LGTM」と伝える

## 手順（引数あり: PR レビュー）

1. `gh pr view <URL or PR番号> --json title,body,files,url` でPR情報を取得
2. `gh pr diff <URL or PR番号>` で差分を取得
3. 以下の観点でレビュー：
   - バグやロジックの誤り
   - セキュリティ上の問題
   - パフォーマンスの懸念
   - テストの網羅性
   - 命名やコードの読みやすさ
4. 問題があれば具体的な修正案を提示、なければ「LGTM」と伝える

## 過去に指摘を受けた観点（必ず通す）

一般的な観点より、実際に指摘されてきたのは以下。差分を見る前に必ずこのリストを開き、1項目ずつ当てる。

### 仕様との突き合わせ（最頻）
- 判定条件・状態のマッピングが、issue / 仕様書 / Notion / Slack の合意と一致しているか
- 状態やステータスの分類は全パターンを列挙し、どこにも入らない／どちらにも入りうる状態がないか
- 判定の粒度は正しいか（ショップ単位 vs 種別単位、アカウント単位 vs 注文単位）
- 過去に「この場合は対象外」と決まった例外が抜けていないか
- 画面文言・メール文面が確定版と一致しているか。用語が既存の呼称と揃っているか

### 既存機能への副作用
- この変更で消える／上書きされるデータはないか
- 継続するはずの機能（計測タグ、設定値など）を巻き添えで消していないか

### nil / 件数の前提
- null を許容する必要が本当にあるか。null 時のフォールバックが表示を壊さないか
- `where` で複数件取る前提が実態と合っているか
- 「あり得ない」ケースを黙って握りつぶしていないか（例外を投げるべきでは）

### 対称性
- 同型の処理が複数ある場合、実装もテストも全部に反映されているか。片方だけになっていないか

### 残骸・後始末
- TODO コメント、デバッグコード、文字化けコメント、使わない定数／カラムが残っていないか
- 依存元PRの最新差分を取り込んでいるか。マージ順の前提がPR本文に書かれているか
- 「なぜこの対応が必要か」「どの入口からのフローか」がコードコメントとPR本文にあるか

### スキーマ変更
- 追加したカラムを実際に使う画面／処理があるか
- NULL 許容とデフォルト値が要件と合っているか
- 既存データの移行コスト・リリース後の対応負荷を考慮しているか

### データ更新SQL
- トランザクションで囲んでいるか。想定行数の検証があるか

## 出力形式

- 観点ごとに見出しを立てて箇条書き
- 各指摘に対象ファイル / 行番号を添える
- 重要度（blocker / nit）を明示
- 些細なスタイルの指摘（nit）は基本的に省略、重要な問題（blocker）だけ指摘する
- ただし**仕様との齟齬が疑われる点は、確信が持てなくても「確認」として必ず出す**（黙って正しいと判断しない）
