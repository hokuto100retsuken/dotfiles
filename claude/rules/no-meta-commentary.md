# 成果物に経緯を書かない

issue / PR の本文・コメント、コードコメント、仕様ドキュメントには**対象そのもの**だけを書く。
経緯・メタ情報はコミットメッセージか issue のコメント側に置く。

- **issue 本文**: 対応内容と確認観点だけ。背景説明・関連issueセクション・結果セクションは足さない（結果はコメントに書く）
- **issue / PR コメント**: 事実だけ。推奨アクション・案A/B/C・「相談させてください」「進め方どうしましょう」等の呼びかけは入れない。提案は求められたときだけ書く
  - **例外: 事実を書いた上で、具体的な意思決定を1つ求めるのは書いてよい。**
    「会員限定ショップは申込がブロックされます。運用上許容できるかご判断ください」のように、
    帰結を先に示して決めることを1つに絞った形。レビュアーが決めるべき論点を黙って自分で倒す方が悪い。
    禁じ続けるのは「この進め方でよいか相談させてください」「案A/B/C のどれがよいでしょうか」のように
    **事実がなく判断を丸投げしている**もの
- **コードコメント**: コードから読み取れない制約・理由だけ。issue / PR 番号・レビュー経緯・仕様書側の記法（①② や §番号）は持ち込まない。説明を長くするより、ガード節などコード構造で意図を表現する
- **仕様ドキュメント**: 仕様の内容だけ。実装PR・承認者名・Slack の経緯は本文に入れず、確定経緯のリンク1つに留める
- 「〜という指摘を受けて」「〜に倣って」の前置き段落は、どの成果物にも書かない

リンクを書くこと自体を禁じるものではない。参考リンクを置くなら淡々と置く（書式は `pr-style.md`）。
