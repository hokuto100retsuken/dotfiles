# セルフレビュー（先回りで指摘する）

コードが動くかどうかより、**仕様と合っているか・既存を壊していないか**でレビュー指摘を受けやすい。
以下は自分で気づいて、確信が持てない点は作業を止めてユーザーに先に伝える。黙って一方に決めない。

## 実装前

- 仕様の出どころ（issue / 仕様書リポジトリ / Notion / Slack の合意）を必ず当たり、コードで書く判定条件と1対1で突き合わせる
- 状態・ステータスの分類やマッピングは**全パターンを列挙**して仕様と照合する。「この状態はどっちに入る？」を残さない
- 判定の**粒度**を明示して確認する（ショップ単位か種別単位か、アカウント単位か注文単位か）
- 過去の会話で「この場合は対象外」「ここでは出さない」と決まった例外がないか探す
- 画面文言・メール文面は草案や確定版と一字一句突き合わせる。用語は既存の呼称に揃える

## 実装中

- **既存機能への副作用**: この変更で消える/上書きされるデータはないか。継続するはずの機能が壊れないか
- **nil / 0件 / 複数件**: null を許容する必要が本当にあるか。`where` で複数取る前提は実態と合っているか。「あり得ない」なら握りつぶさず例外を投げる
- **対称性**: 同型の処理が複数ある場合、実装もテストも全部に対称に反映する。片方だけ直さない
- **条件を厳しくしたら、新しい失敗モードが生まれていないか**: 判定に条件を足す・例外を包み替えると、
  今まで必ず通っていた経路が通らなくなる。次の3つを必ず見る
  - **主経路が失敗したときの回復経路**: 付与・登録の経路が1箇所しかないと、一度取りこぼしたら
    永久にその状態で残る。冪等な再評価点を別に置けないか
  - **read と write で接続先が違わないか**: master へ書いた直後に slave から読むと、
    レプリカラグの間は更新前の行を読む。「保存直後にその値で判定」は疑う
  - **通知・監視が消えないか**: 例外を別クラスで包むと Sentry の `excluded_exceptions` に
    当たって通報が捨てられることがある。分類によって通知の有無が割れないか
- **影響範囲は実データで数える**: 「たぶん影響ない」で通さない。状態ごとに件数を出し、
  0件なら「0件を確認した」と書く。NULL・不正値・境界値の実件数も見る（日付が NULL の行が
  数%あって `Carbon::parse` が TypeError になる、等）。本番参照は Redash の MySQL で足りることが
  多い（BigQuery を使うなら `bigquery-cost` ルール）
- DBスキーマを足すときは、そのカラムを実際に使う画面/処理があるか、NULL 許容とデフォルト値が要件と合っているかを確認する。既存データの移行コストも見る
- **テストは足すより削る**: 「このテストが落ちるとき、どの実装バグを捕まえているか」を1行で言えないなら消す。
  下位クラスでテスト済みの振る舞いを上位でも再テストしない。境界値でないなら1パターンで足りる
- **用語を発明しない**: 新しい語を差分に持ち込む前に `git grep` で既存の多数派を確認し、それに揃える。
  やむを得ず新語を使うなら由来をコメントに残す

## PR作成前

`gh pr create` は hook で `scripts/pre-pr-check.sh` が自動実行され、機械的に判定できる項目
（文字化け・エンコーディング事故・デバッグコード・TODO残骸・依存元から behind・SQLのトランザクション・
テスト差分なし・対称性・lint）は自動で止まる。以下は**機械で見られないので自分で見る**。

- **依存関係**: マージ順の前提をPR本文に書いたか（取り込み漏れ自体は機械が見る）
- **セルフレビューで見つけたことを黙って直さない**: 見つけた事実ごと PR に残す
  （`### セルフレビューで洗い出したエッジケース`、または該当行に
  「〜した理由（セルフレビューで発覚）」の注記）。レビュアーが同じ穴を探す手間が消える
- **背景の明記**: 「なぜこの対応が必要か」「どの入口からのフローの話か」をコードコメントとPR本文の両方に書く
- **根拠の先出し**: レビュー依頼前に、判断の根拠を該当行のインラインコメントとして貼る。
  仕様の出どころ・nil を通した理由・新語の由来・参考にした既存実装・意図的にやらなかったこと。
  手順とトリガー一覧は `/pr` の「自己注記」ステップにある
- 実装で確定した内容を仕様ドキュメントに反映する必要がないか確認する

## 伝え方

- 確信が持てない点は「〜で合っていますか？」と**選択肢付き**で聞く
- 憶測は「憶測ですが」と前置きする
