# セルフレビュー（先回りで指摘する）

コードが動くかどうかより、**仕様と合っているか・既存を壊していないか**でレビュー指摘を受けやすい。
以下は自分で気づいて、確信が持てない点は作業を止めてユーザーに先に伝える。黙って一方に決めない。

## 実装前

- 仕様の出どころ（issue / 仕様書リポジトリ / Notion / Slack の合意）を必ず当たり、コードで書く判定条件と1対1で突き合わせる
- 状態・ステータスの分類やマッピングは**全パターンを列挙**して仕様と照合する。「この状態はどっちに入る？」を残さない
- 判定の**粒度**を明示して確認する（ショップ単位か種別単位か、アカウント単位か注文単位か）
- 過去の会話で「この場合は対象外」「ここでは出さない」と決まった例外がないか探す
- 画面文言・メール文面は草案や確定版と一字一句突き合わせる。用語は既存の呼称に揃える

## 実装中

- **既存機能への副作用**: この変更で消える/上書きされるデータはないか。継続するはずの機能が壊れないか
- **nil / 0件 / 複数件**: null を許容する必要が本当にあるか。`where` で複数取る前提は実態と合っているか。「あり得ない」なら握りつぶさず例外を投げる
- **対称性**: 同型の処理が複数ある場合、実装もテストも全部に対称に反映する。片方だけ直さない
- DBスキーマを足すときは、そのカラムを実際に使う画面/処理があるか、NULL 許容とデフォルト値が要件と合っているかを確認する。既存データの移行コストも見る

## PR作成前

- **残骸**: TODOコメント、デバッグコード、文字化けコメント、使わない定数/カラム
- **依存関係**: 依存元PRの最新差分を取り込んでいるか。マージ順の前提をPR本文に書いたか
- **背景の明記**: 「なぜこの対応が必要か」「どの入口からのフローの話か」をコードコメントとPR本文の両方に書く
- lint / formatter を通す
- 実装で確定した内容を仕様ドキュメントに反映する必要がないか確認する

## 伝え方

- 確信が持てない点は「〜で合っていますか？」と**選択肢付き**で聞く
- 憶測は「憶測ですが」と前置きする
