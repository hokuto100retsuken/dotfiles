# 読み手に届く文章・相談の形

Slack・メール・社外への問い合わせ・issue / PR など、**人が読む文章を書く・添削するとき**に毎回当てる。
ユーザーの依頼文や下書きがこの観点からずれていたら、**そのまま清書せず、ずれを指摘してから直す**。
依頼された問いの立て方に引きずられない。「この聞き方だと〜が返ってこない」と先に言う。

## 書く前に決める

- **誰に向けるか**: エンジニア / 非エンジニア / 社外。相手ごとに必要な情報量は違う。
  全部渡して取捨選択してもらう前提で書かない
- **何を落とすか**: 削るときは「自分と Claude だけが知っている前提を消していないか」を第三者の目で確認する。
  経緯は書かない（`no-meta-commentary.md`）が、読み手が理解に要る前提は削らない
- **道筋がゴールに向かっているか**: 補足を積み重ねて、結論と違う方向に話が流れていないか

## 構成

- 結論・方針を冒頭に置く（「2つのタスクは同時にリリースします」→ 理由・段取り）
- 非エンジニアには内部実装を省き、**何を入れると何が起きるか**だけで説明する
- 相手が「困っている」と言ってきたら、「想定通りの動き」という事実で終わらせず、その先（返答案・回避策）まで出す
- 相手の関心が読めないときは、説明を足すより「気にしているのはどこですか」と聞く
- 用語は入れ子で定義する。定義の中の語がまだ通じないなら、その語も定義する。既存の呼称に揃える

## 判断を仰ぐとき

- 「送りますか？どうしますか？」で投げない。**「自分はこう考える、理由は〜。これでよいか」**の形にする
- 判断そのものを Claude に委ねず、判断に要る材料を集めさせる
- 通知・メール・後処理の要否は、**対になるイベントで何をしているか**から考える
  （受注完了時にオーナー・購入者へ送っているなら、キャンセル時も要る）。オーナー体験・購入者体験を一連のフローで並べる

## 社外への問い合わせ

- 問いは「〜という理解で合っているか」の確認形にする。相手が Yes / No で答えられる形が速い
- 同種の問い（同じ API の同じ失敗系など）は1問にまとめる
- 通常運用でまず起きない事象は単独の問いにせず、近い問いに吸収する
- **性質や宛先が違う問いは混ぜない**（技術仕様と契約・補償、直接の相手と代理店経由の契約）。回答が割れて遅れる
- 質問の前提を疑う。「〜が適用されるか」より「〜に伴い仕様変更の予定があるか」のように、相手が答えられる事実に言い換える
- 抜けやすいので必ず検討する:
  - 状態変化の**通知手段の有無**（webhook 等）。設計に一番効く
  - **テスト環境で再現する方法**。自前で検証できないときの代替になる
- 参照した資料は名称とバージョンを明記する。回答期限は曜日付きで書く
