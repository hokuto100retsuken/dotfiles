# 調査と調査結果の書き方

読み手が**結論だけ読んで動ける**こと、**根拠を1クリックで検証できる**ことを目指す。
文章の一般則は `writing-for-readers.md`、出典リンクの作法は memory の `feedback-evidence-links` に従う。

## 1. 調べ方

書く前に、次の問いに答えられる状態にする。答えられないものは「未確認」として残す。

1. **指摘・報告された1点だけで止めない。同じ形の経路を全部列挙する**
   - 報告された入口は「その1つ」にすぎないことが多い。送り手・呼び出し元・受け手を全部洗い出す
   - 経路ごとに「いつ通るか（条件・フラグ・設定）」と「該当コード」を1対1で持つ
2. **なぜそうなっているかを掴む**: 今の作りの理由（制約・歴史）を1文で言えるようにする。対策の実現性はここで決まる
3. **前提になっている状態を日付付きで固定する**: フィーチャーフラグの割合・対象、設定値、件数。後で変わるので「MM/DD 確認」のように書く
4. **影響を実際に試して確かめる**（テスト環境・テスト用アカウントで）
   - 「何ができてしまうか」を具体的な操作と結果で示す（例: 別の利用者の ID を指定すると 200 とその利用者のデータが返る）
   - 同時に「何はできないか」も確かめて書く。過大評価を防ぎ、区分の根拠になる
5. **確認の強さを項目ごとに区別する**: 「再現した」「コードで確認（実環境での再現は未実施）」「憶測」。混ぜない
6. **区分・優先度は外部の基準に当てる**: 組織のセキュリティ優先度の分類表や一般の評価（RFC・OWASP）を引き、「なぜ1つ上でも下でもないか」を言えるようにする
7. **対策は選択肢を並べてから決める**: 変更が要る箇所の数、既存で使える受け口、本対応と独立に入れられる緩和を分ける

## 2. 書き方の型

```markdown
## 調査結果（MM/DD 時点）

**結論**

- <指摘・論点 1>: <確認の強さ>。区分は <P?>、期日は <日付>。対応は <一文>。残課題は <あれば一文>
- <指摘・論点 2>: ...

### 1. <全体像: 経路・仕組み>
<表: # / 経路 / いつ通るか / 該当コード（パーマリンク）>
<なぜ今そうなっているか>
<前提になっている状態（MM/DD 確認）>

### 2. <影響: 実際に試した結果>
<試した環境・アカウント> / <できたこと> / <できないこと>

### 3. <個別の論点>
- 何が起きるか:
- 原因:
- 今の利用者への影響:
- それでも直す理由:（影響が無いのに直すとき）
- 再現:（どの強さで確認したか）
- 対策:

### 4. 対応の選択肢
- A. ... / B. ...
- 本対応と独立に入れられる緩和:

### 5. 方針・期日
<表: 指摘 / 区分 / 期日 / 内容>
区分の根拠:
- <なぜこの区分か。上でも下でもない理由>
- <見送ったものと、その理由・復活させる条件>

根拠にしたもの:
- <分類表・親 issue・関連 issue・設定・ログ経路・元レポート・依頼元のリンク>
```

### 型を当てるときの約束

- **冒頭の結論は「確認の強さ・区分・期日・対応」を1項目1行で揃える**。本文を読まない人もここで判断できる
- **結論から本文へ章番号で飛べるようにする**（「…を入れる（5 章）」）
- **コードの根拠はコミット SHA 付きのパーマリンク**にする。ブランチ名のリンクは後で行がずれる
  （`git rev-parse origin/<default>` で SHA を取り、`/blob/<SHA>/<path>#L10`）
- 読み手が知らない仕組みは1文で補う（フレームワークの暗黙の挙動など）
- **見送った対策も書く**。理由と、条件が変われば復活させることを添える
- 残課題は隠さず結論に出す
- 章は論点の数に合わせて増減してよい。小さな調査なら「結論＋根拠の表＋根拠にしたもの」まで縮める
- 対応の選択肢（4 章）は、調査の目的に方針決めが含まれるときだけ書く。事実の報告だけを頼まれたら書かない（`no-meta-commentary.md`）

## 3. 投稿前の自己チェック

- [ ] 冒頭の結論だけで「何が・どれくらい・いつまでに・どう直す」が分かるか
- [ ] 報告された1点以外の同型の経路を列挙したか
- [ ] 各主張に、パーマリンク・設定画面・実測のどれかが付いているか
- [ ] 「再現した」と「コードで確認」を書き分けたか
- [ ] できないこと（影響の上限）を書いたか
- [ ] 前提の状態と、本文の時点に日付があるか
- [ ] 区分を外部の基準で説明できているか
- [ ] 投稿前に全文をユーザーに見せて承認を得る
