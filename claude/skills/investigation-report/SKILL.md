# 調査と調査結果の書き方

読み手が**結論だけ読んで動ける**こと、**根拠を1クリックで検証できる**ことを目指す。
文章の一般則は `writing-for-readers.md` に従う。

## 1. 調べ方

書く前に、次の問いに答えられる状態にする。答えられないものは「未確認」として残す。

1. **問いを確定する**: 「何が分かれば、誰が何を決められるか」を1文にする。調査の深さと結論の形はここで決まる
2. **聞かれた1点で止めず、同じ形のものを全部列挙する**
   - 報告された箇所・事例は「その1つ」にすぎないことが多い。同じ処理を通る入口、同じ値を読み書きする箇所、同じ条件に当てはまるケースを洗い出す
   - 1件ごとに「いつ・どの条件で起きるか」と「根拠（コード・設定・データ）」を1対1で持つ
3. **なぜそうなっているかを掴む**: 今の作りや状態の理由（制約・歴史・意図）を1文で言えるようにする。直せるかどうか、直してよいかはここで決まる
4. **前提になっている状態を日付付きで固定する**: 設定値・フラグ・件数・バージョンなど、後で変わるものは「MM/DD 確認」と書く
5. **実際に動かして確かめる**（テスト環境・実データ・ログ）
   - 起きることを、具体的な操作と結果で示す
   - **起きないこと・影響の上限**も確かめて書く。過大評価も過小評価も防げる
   - 件数で語れるものは件数を出す。0件なら「0件を確認した」と書く
6. **確認の強さを項目ごとに書き分ける**: 「実際に確かめた」「コード・資料で確認（実地では未確認）」「憶測」。混ぜない
7. **判断は外部の基準に当てる**: 優先度・要否・期日は、組織の分類表、仕様書、一般の基準（RFC・公式ドキュメントなど）を引いて説明する。「なぜ1つ上でも下でもないか」を言えるようにする
8. **対応は選択肢を並べてから決める**: 変える箇所の数、既存で使えるもの、本対応と別に先に入れられる緩和を分ける

## 2. 書き方の型

```markdown
## 調査結果（MM/DD 時点）

**結論**

- <論点 1>: <答え>（<確認の強さ>）。<判断があれば: 優先度・期日>。対応は <一文>。残課題は <あれば一文>
- <論点 2>: ...

### 1. <全体像: 対象・経路・仕組み>
<表: # / 対象 / いつ・どの条件で起きるか / 根拠（パーマリンク・設定・データ）>
<なぜ今そうなっているか>
<前提になっている状態（MM/DD 確認）>

### 2. <確かめた結果>
<確かめた環境・データ> / <起きたこと> / <起きないこと・影響の上限>

### 3. <個別の論点>
- 何が起きるか:
- 原因:
- 今の影響:（誰に・何件）
- それでも直す理由:（影響が無いのに直すとき）
- 確認の強さ:
- 対応:

### 4. 対応の選択肢
- A. ... / B. ...
- 本対応と別に先に入れられる緩和:

### 5. 方針
<表: 論点 / 判断 / 期日 / 内容>
判断の根拠:
- <なぜこの判断か。上でも下でもない理由>
- <見送ったものと、その理由・見直す条件>

根拠にしたもの:
- <基準・仕様書・関連 issue・設定・データの出どころ・元の報告・依頼元のリンク>
```

### 型を当てるときの約束

- **冒頭の結論は論点ごとに「答え・確認の強さ・判断・対応」を1行で揃える**。本文を読まない人もここで動ける
- **結論から本文へ章番号で飛べるようにする**（「…を入れる（5 章）」）
- 読み手が知らない仕組みは1文で補う（フレームワークの暗黙の挙動など）
- **見送った対応も書く**。理由と、見直す条件を添える
- 残課題は隠さず結論に出す
- 章は調査の大きさに合わせて増減する。仕様確認や件数の確認なら「結論＋根拠の表＋根拠にしたもの」で足りる。判断や対応が無い調査では 4・5 章を書かない
- 対応の選択肢（4 章）は、調査の目的に方針決めが含まれるときだけ書く。事実の報告だけを頼まれたら書かない（`no-meta-commentary.md`）

### 出典リンク

- **主張ごとに出典を1対1で付ける**。読み手は主張そのものより「どこに書いてあるか」を確かめたい
- **コードはコミット SHA 付きのパーマリンクにし、行番号まで付ける**。ブランチ名のリンクは後で行がずれる
  - SHA は `git rev-parse origin/<default>`、行番号は `git show origin/<default>:<path> | grep -n` で取る。作業ブランチの行番号は使わない
  - 形式: `https://<host>/<org>/<repo>/blob/<SHA>/<path>#L10-L20`
- 一次情報を優先する: 公式ドキュメント・仕様書 > API 定義（OpenAPI など） > 設計ドキュメント > 実装コード・コミット・PR
- 定義ファイルの値1つ（enum など）だけで断定しない。挙動は別の一次情報か実測で裏を取る

## 3. 投稿前の自己チェック

- [ ] 冒頭の結論だけで、問いへの答えと次の動きが分かるか
- [ ] 聞かれた1点以外の、同じ形のものを列挙したか
- [ ] 各主張に、パーマリンク・設定・実測のどれかが付いているか
- [ ] 「実際に確かめた」と「コード・資料で確認」を書き分けたか
- [ ] 起きないこと（影響の上限）を書いたか
- [ ] 前提の状態と、本文の時点に日付があるか
- [ ] 判断を外部の基準で説明できているか
- [ ] 投稿前に全文をユーザーに見せて承認を得る
